`host-gateway` would resolve to the engine-wide gateway, not this dedicated link. The mapping sends traffic over the API's connected route. The normal application bridge stays in place for nginx, DB egress, and the loopback-only `127.0.0.1:8011` API binding. The dedicated bridge must use ordinary internal bridge mode, **not** `gateway_mode_ipv4=isolated` (which removes the host-facing bridge address). The network is external so it can be checked and used for preflight before an application container is attached; Compose does not create, reconcile, or remove it. Missing or incompatible external IPAM must block deployment; never substitute the shared bridge.

Before an approved host change, Sthira must verify the addresses do not overlap with Docker, host, VPC, or VPN ranges, reserve the name and IPAM above, and confirm the bridge settings, lack of other members, exact host bind and effective firewall rule order. The persistent host guard must allow TCP `8643` only on the verified veth of the approved `aethos-ps` Compose `api` service, from `172.31.254.2` to `172.31.254.1`, then deny other IPv4 and all IPv6 access to that port before any broad legacy allows. Do not use dynamic IPs, the shared subnet, or a second permit for a probe. There is no Docker or Traefik publication of `8643`. Docker/root access is privileged and must be restricted.

Only `api` receives the Hermes bearer, broker token, and context signing secret. The bearer must match the dedicated listener's `API_SERVER_KEY`/`HERMES_API_SERVER_KEY`; the broker token is separately shared with the dedicated host profile; the signing secret stays API-side. Verify all three are set without rendering or dumping an environment. The Procrastinate worker does **not** require Hermes: the runtime builder is called by the HTTP chat endpoint, while the worker's registered tasks use their own paths (including the in-process `CopilotAgent` for finance-ops). Worker provider credentials are unchanged. Neither worker nor `migrate` gets the dedicated network, hostname mapping, or Hermes secrets. Host-to-ERP tool access remains on the existing broker path; it is not proven by the inference probe.

### Host guard and startup interlock (PR #593)

The boot unit installs a closed `inet aethos_hermes_530` INPUT table (priority `-10`, before the conventional filter chain) and an empty `bridge aethos_hermes_530` INPUT chain. Both tables are replaced in one nft transaction. In the closed state all TCP `8643` is dropped in both IP families. An `ACCEPT` in the legacy filter chain cannot undo this table's `DROP`. Conversely, a scoped `ACCEPT` here cannot override the legacy IPv4 drop: the helper inserts a single tagged exact permit at the head of iptables-nft INPUT while the nft policy is still closed. No unrelated rule is modified.

The drop-in requires closed-table readback and fresh Docker/IPAM/host/legacy/port evidence before `ExecStart`. The exact approved container must be the sole dedicated-network member, running and not paused/restarting, with the approved release tag and immutable local image ID. Docker network and container snapshots must agree on network/endpoint IDs, address and MAC. The controller checks the PID's network namespace against Docker's sandbox, the connected route/source, and reciprocal veth indices between that namespace and the sole Linux bridge port. `ExecStartPost` verifies the exact socket and systemd main PID, and rechecks identity before and after opening. The bridge-family INPUT rules require the physical veth's ifindex, name and source MAC for listener traffic; the inet-family rules additionally require bridge ifindex/name, source `.2`, and both original and current destination `.1:8643`. There is no established-session exception. Removing the veth fences packets immediately, without waiting for a Docker event or poll. A replacement on the same bridge and IP does not inherit the permit. `ExecStopPost` restores the deny and removes only the exact tagged compatibility permit. Stopping/restarting the guard or Docker stops the listener through `BindsTo`; the guard unit does not start the listener. Before any planned API recreation or endpoint change, stop the listener, revoke the approval and verify closed readback; after an unexpected identity change, do the same before investigating. No automatic readmission. Do not reuse interface indices administratively, graft the approved veth into a different namespace, attach alternate members, or allow external firewall modifications while open. The guard does not defend against privileged host/Docker operators or replace listener authentication.

From the repository root, on a Linux test host with `CAP_SYS_ADMIN` and `CAP_NET_ADMIN`, run `python3 -I -B integrations/hermes/host/test_guard_netns.py`. The suite creates disposable network namespaces and runs the actual nft/iptables code against synthetic legacy rules. No server is started: a reset on the permitted path proves it reached local socket lookup; a timeout on denied paths proves it did not. The same-bridge replacement keeps the address, MAC and veth name but gets a new ifindex and remains denied. This does not prove the live Docker path, systemd boot, BPF enforcement, Hermes authentication, or app behavior.

## Rollback (not performed by this task)

- **Before deploy:** stop at the failed gate and discard the staging changes if needed. Leave the host guard closed; never re-enable shared access as a workaround.
- **If a later approved rollout fails:** restore the recorded last-known-good Compose revision, image SHA and runtime env via the approved release path. For Basic-only recovery set `ATLAS_AI_RUNTIME=aethos_basic` and account for explicit tenant Hermes overrides (they take precedence). Apply the rollback through the API release configuration, not a restart that would retain stale env. Verify `/health/ready` and its build SHA, loopback broker/nginx access and a known-safe Basic turn. No database rollback is required by this change.
- **Review-branch rollback:** revert the host-guard commit on the existing PR branch. No host rollback is needed for offline validation.
- **If a later authorized host guard deployment fails:** halt cutover. Stop and disable only `aethos-hermes-runtime.service` and verify no process is listening on TCP `8643` (IPv4 or IPv6). Remove the approval file. Run the installed controller's `close` action and verify the closed inet INPUT table and absence of the tagged IPv4 permit. Keep the deny-only guard enabled so the closed state survives reboot. Restore only the reviewed dedicated listener drop-in changes from the pre-change record; keep the listener disabled, reload units after approved edits, and verify unaffected rules/services. If close or readback fails, keep the listener off and escalate; do not delete the deny table, flush/restore the shared firewall, reinstate broad permits, start the legacy listener, or touch the team gateway. Remove the bridge only if unused and separately approved. Do not restart until exact bind and both effective firewall paths are reverified under fresh approval.
