# Dedicated Telegram ERP bot (#595)

**Off by default.** This is an optional pilot adapter, not a Hermes Telegram gateway. Do not activate on any production deployment until #530 is accepted, Prahari has reviewed this feature, and the synthetic staging checklist has passed. Telegram bot DMs are **not end-to-end encrypted**; `protect_content` reduces forwarding, not screenshots or device compromise. Get workspace approval before sending even an aggregate balance through Telegram. Keep records and detailed reviews in Aethos.

## Staging setup (operator only)

1. Use a fresh, dedicated BotFather bot and a synthetic-only Aethos database. Do not reuse the team/broadcast bot, a Hermes bot, credentials, or bot username between environments. Disable group joining (`/setjoingroups`) and inline mode in BotFather. Keep the bot token in the operator secret store; the Aethos runtime does **not** need it.
2. Apply `0123_telegram_erp.sql` using the normal migration runner on the isolated database. Keep `TELEGRAM_ERP_ENABLED=false` during rollout. Both Hostinger Compose variants forward the `TELEGRAM_ERP_*` variables to the API only. Use the environment's secure secret injection, not repository files, CI logs, or rendered Compose output. The production deployment workflow intentionally does not provision these secrets.
3. Generate an independent high-entropy Bot API webhook secret (e.g. 32 random bytes encoded as hex). Set `TELEGRAM_ERP_WEBHOOK_SECRET` on the API with that exact value (32–256 URL-safe characters). Do not reuse Aethos JWT, Atlas broker, or Bot API credentials. Use TLS at the edge. Forward only `POST /api/v1/telegram/webhook` to the API with the standard `X-Telegram-Bot-Api-Secret-Token` header intact; do not expose the Atlas broker or the private Hermes listener for this adapter. Configure request size/rate limits and disable request/response body and credential-header capture at the edge/APM. Do not use an endpoint URL containing a secret.
4. From a secure operator client, call Telegram Bot API `setWebhook` with `url=https://<staging-host>/api/v1/telegram/webhook`, `secret_token` set from the secret store, `allowed_updates=["message"]`, `drop_pending_updates=true`, and low `max_connections` (e.g. `2` for the pilot). Use a client that redacts the Bot API token in its URL and the webhook secret in its body; do not paste credentials into terminal history or screenshots. Check `getWebhookInfo` for the exact intended host, allowed updates, and delivery errors. If standard edge forwarding is used, ensure there is only one registered webhook and one bot per Aethos database. Do not run polling alongside the webhook.
5. Set `TELEGRAM_ERP_ENABLED=true` **only in synthetic staging** and restart/redeploy the API there. Execute [the scenario](../test/e2e_telegram_erp.md). No real ERP writes or production accounts for verification.

## Link, use, revoke

1. Send `/id` to your dedicated bot in a private DM. From an authenticated Aethos session in the intended workspace, call `POST /api/v1/telegram/link` with the usual bearer and `X-Tenant-ID` plus `{ "sender_id": <numeric ID from your own DM> }`. There is no new SPA screen in this pilot; use a trusted first-party API client and do not copy ERP session tokens into Telegram. Never use someone else's sender ID or link payload. The response is non-cacheable and has a one-use `start_payload`, valid for five minutes; send `/start <start_payload>` to the same bot from the same private account. Only this verified sender can redeem the challenge. One sender can link to one workspace/account at a time (30-day maximum).
2. `/ar` shows only the posted AR total in base currency. `/draft <engagement UUID> <start YYYY-MM-DD> <end YYYY-MM-DD>` previews an Inbox request; `/confirm <code>` from the same link within five minutes authorizes the request. Each code is bound to the exact arguments. Confirming checks current membership, billing, `invoices.draft` and the existing Copilot tool policy. It can only create an Inbox review, never post/send an invoice, pay, or approve. Check Inbox before retrying a change with an uncertain result; Telegram's webhook reply method cannot report delivery success to Aethos. Other requests belong in authenticated Nous.
3. `/unlink` from the linked DM or `DELETE /api/v1/telegram/link` (own ERP bearer and workspace header) revokes the link immediately for subsequent operations, including staged confirmations. Changing workspaces requires revocation before relinking. Pending challenges may also be revoked from the ERP. Revocation does not cancel a broker call already in flight or remove an Inbox item previously queued. Review or dismiss the item through normal ERP permissions.

## Incident response and retention

- Disable the feature on **all** API replicas first. Remove the Telegram webhook and drop queued updates. If a token or webhook secret may be exposed, revoke/rotate both independently, invalidate links and pending challenges, and review the audit ledger and ERP Inbox before reopening. Do not assign a replacement bot to an existing pilot without resetting the bot-specific delivery ID namespace under approved retention controls. Never repoint this bot at a different database with existing user links.
- `telegram_erp_deliveries` is service-role-only. It records update ID, Aethos tenant/user/link, command, outcome and optional suggestion ID; ERP chat history records supported tool turns. No raw command text, bot usernames, access tokens, or plaintext challenges are written to these tables. `claimed` with no final outcome may mean the operation failed or committed before the webhook reply. The handler will not replay that operation automatically. Follow the ERP Inbox/audit trail instead.
- Have the database operator schedule approved retention: remove expired links, clear expired confirmation hashes/arguments, and retain audit rows per workspace policy (and at least 24 hours; webhook input freshness is five minutes). Do not delete recent delivery or confirmation rows to make a retry work. An expired active sender row can reserve its unique sender until deleted; remove it via ERP revocation or expiry cleanup before moving the sender. On rollback, keep the additive tables private for audit; no destructive schema rollback is required.
